# 00. 제출용 요약 — VC ERP (LP)

> 출자기관(LP)이 **여러 GP의 여러 조합**에 한 출자를 **계획 → 심사·선정 → 약정 → 납입 → 사후관리 → 회수·성과 분석 → 청산**까지 한 시스템에서 처리하는 ERP MVP.
> 같은 작업 폴더의 GP 시스템([`vc-erp/gp`](../../gp/docs/00_summary.md))과 연동 API·웹훅으로 **양방향** 연결된다. 개인 연구 목적 프로젝트이며 실제 서비스와 무관하다.

- 배포: LP <https://vc-erp-lp.vercel.app> · GP <https://vc-erp-gp.vercel.app> (둘 다 데모 전용 DB, 매일 03:00 KST 초기화)
- 소개 페이지(로그인 없이, 캡처 · 연동 · QA 한 장): <https://vc-erp-lp.vercel.app/intro>
- 로그인: 첫 화면의 **데모로 둘러보기**에서 기관(하늘연금 · 바다성장출자)과 역할(출자 담당 · 결재권자 · 관리자)을 고른다

## 1. 한 줄 요약

여러 기관이 함께 쓰는 서비스(기관별 데이터 완전 분리)에서, LP의 핵심인 **결정(심사·결재) · 확인(대사) · 모아 보기(성과 분석)** 를 끝까지 이어지게 만들었고, 우리 GP 시스템의 조합은 **웹훅으로 자동으로 들어오고 LP의 결정(선정·투표·확인)이 GP로 되돌아간다.**

## 2. 만든 것 (릴리스별)

| 릴리스 | 내용 | 주요 화면 |
|---|---|---|
| R0 | 별도 Next.js 앱 · Neon DB · Vercel 프로젝트, 데모 로그인(기관 2곳 × 역할 3개) | 로그인 |
| R1 | 기관·사용자·역할(서버 한곳에서 권한 검사), 운용사·조합(수기), 감사 로그, 기관 분리(복합 외래 키 + 서비스 함수가 기관 ID를 첫 인자로) | 사용자 · 운용사 · 조합 |
| R2 | 출자 예산(분야별 배분), 출자사업 공고(모집 부문), 출자 제안 접수(공고형·개별형), 심사 단계·평가표(가중 점수), 선정 조건, **선정 결재**(예산 잔액·부문 한도 차단) | 출자 예산 · 출자사업 · 출자 제안 · 결재함 |
| R3 | **GP 연동**: 웹훅(HMAC) 받기 → 인박스 → 처리, 놓친 이벤트 가져오기, 연동 GP 제안 자동 접수, **선정·탈락을 GP에 전달**(GP 화면 "LP 직접"), 결성 확인(확인표), 가져온 출자 건, LP 배포 · 배포 환경끼리 연결 · 데모 DB 매일 초기화 | 출자 건 · GP 연동 |
| R4 | 캐피탈콜 수신 → **납입 결재** → 송금 기록 → **GP 원장과 대사**(확인 대기 7일), 과거 납입 가져오기, 자금 계획(확정 + 추정) | 캐피탈콜 · 자금 계획 |
| R5 | 통지함(받음 확인 → GP), GP 보고 수집·검토·조건 준수 점검, **총회 투표 결재 → GP에 직접 투표**, 핵심 운용 인력 변경 감지, 주의 목록 | 통지함 · GP 보고 · 총회 · 대시보드 |
| R6 | 분배 수신 → **수령 기록** → 분배 대사, 성과 지표(DPI · RVPI · TVPI · XIRR, 기준일 선택, 조정 평가액), 포트폴리오(빈티지·분야·운용사·연동/수기), **청산 확인**(조건표 → 최종 성과 고정 → 잠금) | 분배 · 성과 |
| R7 | 대시보드(예산 사용 · 포트폴리오 · 이번 달 납입 예정 · 30일 일정 · 차트 3개), **숫자 일치 점검 스크립트**, 전 단계 데모 시나리오 스크립트, 이 요약 | 대시보드 |
| R8 | **출자사업 공고 게시판**(모든 기관 공고, 연동 GP에 서명 API로 공개) · GP가 공고 부문에 지원 → LP가 그 부문에 자동 접수 · 선정 조건을 GP에 보내 "앵커 조건"(필요한 최소 결성액 · 남은 모집액 · 결성 기한) · GP 조합 분야 | 공고 게시판 · (GP) 출자사업 공고 · 앵커 조건 |

규모: 마이그레이션 10개, 테이블 36개, 계산용 뷰 5개, 내부 API 라우트 95개 + 웹훅 받기 1개 + 주기 작업 2개, 화면 37개. GP 쪽에는 LP를 위한 API 4가지를 더했다 (출자 제안 목록·응답, 보고의 LP 몫 평가액, 의무 비율·운용 인력 변경 이벤트 — [05](05_api_design.md) 5장).

## 3. 화면 구조

- **사이드바 8줄 + 묶음 안의 탭** (`lib/nav.ts`, 자주 여는 순): 대시보드 · 결재함 / **납입·분배**(캐피탈콜 · 분배 · 자금 계획) · **사후관리**(통지함 · GP 보고 · 총회) · **출자 심사**(출자 제안 · 출자사업 · 출자 예산) · **포트폴리오**(출자 건 · 성과) / **조합·운용사** / 관리자: **기관 설정**(사용자 · GP 연동 · 평가 항목 · 감사 로그)
- **출자 건 상세** 한 화면에 그 출자의 전 과정: 선정 조건 → 결성 확인표 → 성과(기준일 선택) → 캐피탈콜 → 분배 → 우리 장부 / GP 원장 사본 · 대사 이력 → 청산 확인

## 4. GP 연동 구조

```
GP 시스템 (원본)                                   LP ERP (출자자)
  출자 제안 발송 ──웹훅(HMAC)──→ 인박스 → 제안 자동 접수
                ←──제안 응답 API── 선정·탈락 결재 승인          (GP: "확약 · LP 직접")
  결성 · 원장   ──웹훅──→ 동기화: GP API 다시 읽기 → 원장 사본 → 대사
  캐피탈콜      ──웹훅──→ 콜 수신 → 납입 결재 → 송금 기록 → 납입 대사 "일치"
  보고 · 총회   ──웹훅──→ 보고(우리 몫 평가액) · 총회 안건
                ←──투표 API── 투표 결재 승인                  (GP: "LP 직접" 투표)
  통지          ──웹훅──→ 통지함 ──받음 확인──→ GP
  분배 확정·지급 ──웹훅──→ 수령 대기 → 수령 기록 → 분배 대사 "일치"
```

- **이벤트는 신호일 뿐**: 웹훅을 받으면 내용을 믿지 않고 GP API를 다시 읽어 맞춘다. 놓쳐도 다음 동기화가 맞춘다 (매일 주기 작업 + 관리자 "지금 가져오기")
- **우리 장부와 GP 원장 사본을 따로** 두고 비교한다(대사). 송금일과 GP 입금 확인일이 다른 것은 정상이라 7일은 "확인 대기"
- **GP에 보내는 것**(선정 응답·받음 확인·투표)은 저장이 먼저, 전송은 그다음. 못 보내면 표시하고 주기 작업이 다시 보낸다

## 6. 설계 원칙

| 원칙 | 구현 |
|---|---|
| 기관 분리 (L2) | 모든 표에 `org_id`, 기관을 건너는 연결은 복합 외래 키로 DB가 막고, 서비스 함수는 기관 ID를 첫 인자로 받는다. 다른 기관 ID는 404 |
| 장부는 추가만 | 우리 장부 · GP 원장 사본 · 대사 이력 · 단계 이력은 DB 트리거로 수정·삭제 차단. 정정은 취소 행(원래 날짜 또는 오늘 날짜) |
| 결재 없이 돈이 안 나간다 (L4) | 선정 · 납입 · 투표는 결재 승인 뒤에만. 결재 때 숫자를 스냅샷으로 남기고, 승인 순간 다시 검사(예산 행 잠금) |
| 숫자는 한 곳에서 | 성과·예산·자금 계획은 저장하지 않고 계산. 대시보드는 각 화면과 **같은 함수**를 부른다 → 점검 스크립트가 89개 항목을 비교 |
| 세 겹의 방어선 | 화면 검사 → 서버 업무 규칙(오류 코드 + 규칙 ID) → DB 제약·트리거 |
| 중복 방지 | 돈이 걸린 요청은 `Idempotency-Key`, 받은 웹훅은 이벤트 ID로 한 번만 |
| 연동은 끊겨도 된다 | GP가 응답하지 않아도 LP 업무는 저장되고, 못 보낸 것·못 받은 것은 주기 작업과 수동 버튼이 맞춘다 |

## 7. 단순화한 가정 (⚠️ 실무 확인 필요)

전체 목록은 [98 실무 확인 목록](98_practice_check.md) (30개). 대표적으로:

- 결재자 한 명(결재선·전결 규정 없음), 심사위원 역할 없음(담당·결재권자가 평가)
- 분야별 배분 초과·선정 GP 수 초과는 경고만, 결성 기한이 지나도 자동 취소하지 않음
- 대사 확인 대기 7일(달력일), 보고 기한 분기 말 + 45일
- 자금 계획 추정 = 남은 약정을 투자 기간 끝까지 매달 똑같이
- 성과 평가액 = 최근 보고 + 이후 납입 − 이후 분배(롤포워드), 첫 납입 90일 미만이면 IRR 표시 안 함, 분배 세금 미반영

## 8. 기술 스택

Next.js 16 (App Router, Route Handlers), TypeScript, Tailwind CSS, PostgreSQL(Neon) + postgres.js로 SQL 직접 작성, zod 검증, Vercel(싱가포르 서버, Cron 하루 1회). 차트는 라이브러리 없이 막대로 직접 그렸다 (L44).

## 9. 실행 방법

```bash
npm install
npm run db:migrate          # 마이그레이션 001~010
npm run db:seed             # 데모 기관 2곳 × 역할 3개 계정 → demo-accounts.md
npm run gp:link             # GP 연동 설정 (GP 쪽 npm run db:seed-lp-demo 먼저)
npm run db:seed-scenario    # 전 단계 데모 시나리오 (있으면 건너뜀)
npm run dev                 # http://localhost:3200 (GP는 3000)
npm run check:numbers       # 숫자 일치 점검 (-- --demo 는 배포 데모 DB)
```

배포 데모 갱신: GP `npm run db:demo-refresh -- --prune-backups` 가 성공한 뒤 LP 같은 명령 → `vercel deploy --prod` (짝 맞춘 갱신, L26·L33).

## 10. 남은 과제 (고도화)

- 결재선(여러 단계) · 전결 규정, 심사위원 역할과 위원별 평가
- 수기 조합 핵심 운용 인력 변경 감지, 수기 보고 PDF 올리기(파일 저장소)
- 한 기관이 여러 GP 시스템에 연결될 때의 통지 배정, GP에 선정 취소·콜 취소 API
- 공휴일 달력(영업일 기준 확인 대기), 조합별 보고 주기, 분배 원천징수
- 유료 요금제에서 주기 작업 간격 단축(지금 하루 1회)
