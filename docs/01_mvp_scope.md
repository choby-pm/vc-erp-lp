# 01. MVP 범위 (v2)

> 변경 이력
> - v1 (2026-09-29): LP 시스템을 **LP 기관용 ERP**로 정하고 첫 범위 초안 작성 (L1)
> - v2 (2026-09-29): 정할 것 Q1~Q5를 모두 기본안으로 확정 (L2~L6). 여러 기관이 쓰는 서비스, 공고형·개별 제안형 모두, 내부 결재 3곳, GP 시스템에 API 추가, GP 데이터 읽기 전용 사본 저장
>
> ⚠️ 표시는 실무 규칙 확인이 필요한 부분이다. GP 때처럼 단순화한 규칙으로 구현하고, 그 사실을 화면과 문서에 밝힌다.

## 1. 목표

출자기관(LP)이 **여러 GP의 여러 조합**에 한 출자를 **계획 → 발굴·심사 → 약정 → 납입 → 사후관리 → 회수·성과 분석**까지
한 시스템 안에서 처리해볼 수 있게 한다.

- **여러 출자기관이 함께 쓰는 서비스(SaaS)** 로 만든다. 기관마다 데이터가 완전히 분리된다 (L2).
- 우리가 만든 GP 시스템(`vc-erp/gp`)은 이 LP ERP에 연결된 **GP 중 한 곳**이 된다.
  그 GP의 조합은 연동 API·웹훅으로 데이터가 자동으로 들어오고, 다른 GP의 조합은 담당자가 직접 입력한다.
- 보여주고 싶은 것: **출자자 쪽 업무 흐름 이해**, **두 시스템 사이의 양방향 연동·대사(맞춰보기) 설계**, **여러 조합을 모아 보는 성과 분석**, **기관별 데이터 분리**.

## 2. "얇지 않은 기능"의 기준 (GP와 같음)

1. **입력 → 처리 → 결과**가 끝까지 이어진다
   (예: 캐피탈콜 수신 → 납입 결재 → 납입 기록 → GP 원장과 금액 일치 확인)
2. **다음 단계가 앞 단계의 데이터를 그대로 이어받는다**
   (예: 심사에서 정한 출자 예정액이 약정액이 되고, 약정액이 납입·자금 계획·성과 계산의 기준이 된다)
3. **실무에서 막아야 할 실수를 시스템이 막는다**
   (예: 출자 예산 초과 선정, 약정액 초과 납입, 결재 없는 납입 기록, GP 데이터와 다른 금액을 모르고 넘어가기, 다른 기관 데이터 보기)

## 3. GP와 LP의 역할 차이 (한눈에)

- GP는 **조합 하나를 운영**한다. 원본 데이터(약정·납입·분배·투자)를 만든다.
- LP는 **여러 조합에 돈을 넣은 투자자**다. 원본을 만들지 않고, GP가 보낸 숫자를 받아
  **우리 돈이 제대로 나가고 들어왔는지 확인**하고, **전체 출자 포트폴리오의 성과**를 본다.
- 그래서 LP ERP의 핵심은 "계산"보다 **결정(심사·결재)**, **확인(대사)**, **모아 보기(분석)** 다.

## 4. LP 업무 전체 지도

> 국내 출자기관(정책 출자기관, 연기금·공제회, 금융기관)의 일반적인 절차를 기준으로 한 초안이다.

### 단계 1. 출자 계획
- 연도별 출자 예산: 총액, 분야별(예: 초기·성장·세컨더리·해외) 배분 목표 ⚠️
- 예산 사용 현황: 선정액·약정액·납입액이 예산 대비 얼마인지 자동 집계
- 선정 금액이 그해 예산 잔액을 넘으면 **차단**

### 단계 2. 출자사업 · 출자 제안 접수 (L3: 공고형·개별 제안형 모두)
- **출자사업 공고**(정책 출자기관 방식): 사업명, 모집 부문(분야, 부문별 출자 예정액, 선정 GP 수, 최소 결성 규모, 출자 비율 상한), 접수 기간
- **개별 제안**(연기금·금융기관 방식): 공고 없이 GP가 보낸 출자 제안을 건별로 검토
  - 연동 GP의 **출자 제안 통지**는 자동으로 개별 제안이 되어 검토 목록에 들어온다
- 두 방식 모두 **"출자 제안" 한 건**으로 통일해 같은 심사 흐름을 탄다. 공고를 통해 들어왔는지만 구분한다
- 제안 내용: GP·조합 계획(목표 결성액, 존속·투자 기간, 보수 조건, 핵심 운용 인력), 요청 출자액
- 운용사(GP) 기준 정보: 운용사명, 유형, 운용 규모, 담당자, 과거 조합 이력

### 단계 3. 심사 · 선정
- 심사 단계: 서류 심사 → 현장 실사 → 대면(PT) 심사 → 투자심의위원회 → 선정 / 탈락 ⚠️ 기관마다 단계가 다름
- 심사위원 평가표: 항목별 점수(운용 인력, 운용 성과, 투자 전략, 조합 조건 등)와 가중 합계, 의견
- 선정 조건: 출자 예정액, 출자 비율 상한, **결성 기한**, 핵심 운용 인력 유지 조건 ⚠️
- **선정 결재** (L4) → 승인되면 선정 확정(= 출자 확약)
- 연동 GP 제안이면 **선정·탈락 결과를 GP에 전달**해 GP의 출자 제안이 "확약"·"거절"로 바뀐다 (L5)

### 단계 4. 약정 · 결성 확인
- 결성 확인: 결성 기한 안에 최소 결성 규모를 채웠는지, 출자 비율 상한을 넘지 않는지 점검
- 약정 확정: 최종 약정액, 조합 전체 결성액, 우리 지분율
- 결성 기한을 넘기면 **선정 취소** 처리 ⚠️
- 연동 GP 조합: GP의 결성·약정 원장이 들어오면 **선정 조건과 자동 비교**

### 단계 5. 납입 · 자금 관리
- **캐피탈콜 수신**: 연동 GP는 자동, 그 외는 입력 (회차, 요청액, 납입 기한)
- **납입 결재** (L4): 기안 → 승인 / 반려. 승인되지 않은 납입은 기록할 수 없다
- **납입 기록**: 납입일·금액, 남은 약정액 자동 차감, 약정액 초과 차단
- **대사**: 우리 장부의 납입 합계 ↔ GP 원장의 납입 합계 비교, 다르면 "불일치"로 표시
- **자금 계획**: 조합별 남은 약정액과 남은 투자 기간으로 향후 납입 예상액을 월·분기별로 추정 ⚠️ 추정 방식 단순화

### 단계 6. 사후관리
- 조합별 현황: 약정·납입·분배·평가액(NAV)·남은 약정
- **GP 보고 수집**: 연동 GP의 정기 보고(스냅샷·PDF)는 자동, 그 외는 입력·첨부. 보고 기한을 넘기면 경고
- 의무투자 등 **약정 조건 준수 점검**: 보고서 숫자로 확인, 미달 경고 ⚠️
- **총회 의결권 행사**: 안건 수신 → 내부 검토 의견 → **투표 결재** (L4) → 찬반 확정 → 연동 GP는 API로 직접 투표 (GP의 D40 기능 사용)
- 통지함: GP에서 받은 모든 통지와 확인 처리 (연동 GP는 확인 결과를 GP에 전달)
- 주의 목록: 납입 기한 임박, 대사 불일치, 보고 미제출, 결성 기한 임박·초과, 핵심 운용 인력 변경, 결재 대기

### 단계 7. 회수 · 성과 분석 · 청산
- **분배 수령**: 분배 통지 수신 → 수령 기록 → GP 원장과 대사 (원금 반환·수익 구분)
- **성과 지표**(조합별 · 전체): 납입 대비 총가치 배수(TVPI), 분배 배수(DPI), 잔여 가치 배수(RVPI), 내부수익률(IRR) ⚠️ 계산 기준일·평가액 기준 단순화
- **포트폴리오 분석**: 결성 연도(빈티지)별, 분야별, GP별로 모아 보기
- 해산·청산 확인: 최종 분배 후 출자 건 종료 처리, 최종 성과 고정

## 5. 설계 원칙

### 5-1. 기관별 데이터 분리 (L2)
1. 기관이 만든 모든 데이터에는 **기관 ID**(`org_id`)가 붙는다
2. 모든 조회·수정은 **로그인한 사용자의 기관 ID로 거른다**. 이 검사는 서버 한 곳에서 하고, 화면이나 개별 API에 맡기지 않는다
3. 다른 기관의 데이터 ID를 주소에 넣어도 "없음"(`404`)으로 답한다 (존재 여부도 알려주지 않는다)
4. 데모에 기관 2곳을 넣어 분리를 보여준다

### 5-2. 내부 결재 (L4)
- 결재를 거는 곳은 **출자 선정, 납입, 총회 투표** 세 곳이다
- 흐름: 기안 → 결재 대기 → 승인 / 반려. 반려되면 고쳐서 다시 기안할 수 있다
- 기안한 사람은 자기 건을 결재할 수 없다
- 결재선(여러 단계 결재)은 고도화로 미루고, MVP는 결재자 한 명 ⚠️

### 5-3. GP 시스템 연동
1. **연동 조합과 수기 조합을 같은 구조로 다룬다**
   모든 조합 데이터에 출처(`gp_api` / `manual`)를 남긴다. 화면과 성과 계산은 출처와 상관없이 같은 방식으로 동작한다.
2. **GP 데이터와 우리 장부를 나눠서 저장하고 서로 맞춰본다 (대사)** (L6)
   - GP 원장 사본: GP가 보낸 약정·납입·분배 기록 (연동 조합만. 받은 그대로 저장, LP ERP에서 고치지 않음)
   - 우리 장부: 우리가 결재하고 실제로 보낸·받은 돈의 기록
   - 두 합계가 다르면 불일치로 표시하고, 담당자가 확인 메모를 남긴다
3. **GP에서 받는 데이터는 멱등하게(같은 것을 두 번 받아도 한 번만 반영) 저장한다**
   웹훅은 `X-GP-Event-Id` 로 중복을 거르고, 놓친 이벤트는 `GET /events?after=` 로 다시 가져온다.
4. **GP로 보내는 것** (L5)
   - 이미 GP에 있는 API: 통지 확인, 총회 투표
   - GP에 새로 추가할 API: 출자 제안에 대한 응답(확약 금액 또는 거절)
5. **연동 한 건 = LP ERP 전체 ↔ GP 시스템 하나**
   GP 연동 API는 시스템 전체가 API 키 하나를 쓰고 주소에 GP 쪽 출자자 ID(`lp_id`)를 넣는다 (GP D24).
   그래서 LP ERP는 **"우리 기관 = GP의 어떤 출자자"** 연결표를 두고, 기관 사용자가 자기 기관에 연결된 `lp_id` 로만 호출하도록 서버에서 막는다.
   GP가 한 웹훅 주소로 모든 출자자의 이벤트를 보내므로, 받은 이벤트는 `lp_id` 로 기관을 찾아 나눠 담는다.

## 6. 개발 순서 (릴리스)

- **R0** 개발 환경: 별도 Next.js 앱, 별도 Neon DB, 별도 Vercel 프로젝트, 별도 GitHub 저장소, 데모 로그인(기관 2곳)
- **R1** 기준 정보: 기관·사용자·역할, 운용사(GP), 조합 등록(수기), 기관별 데이터 분리 검사
- **R2** 출자 계획 · 출자사업 공고 · 출자 제안 접수 · 심사 평가 · 결재 기능 · 선정
- **R3** GP 연동: 연동 설정, 웹훅 수신, 놓친 이벤트 가져오기, 연동 GP 제안 자동 접수, **GP에 제안 응답 API 추가** · 약정 · 결성 확인
- **R4** 캐피탈콜 수신 · 납입 결재 · 납입 기록 · 대사 · 자금 계획
- **R5** 사후관리: 보고 수집, 조건 준수 점검, 총회 의결권 행사(투표 결재 → GP 직접 투표), 통지함, 주의 목록
- **R6** 분배 수령 · 성과 지표 · 포트폴리오 분석 · 청산 확인
- **R7** 대시보드, 전 단계 데모 데이터, 제출용 요약, 배포

## 7. 성공 기준

데모 기관으로 아래 시나리오를 처음부터 끝까지 막힘없이 진행할 수 있다.

1. 올해 출자 예산을 정하고 출자사업을 공고 → GP 3곳이 제안 → 심사 평가 → 결재 → 2곳 선정 (예산 초과 선정은 차단)
2. 선정한 조합 중 하나는 **우리 GP 시스템**의 조합이다. LP ERP에서 선정하면 GP 화면의 출자 제안이 "확약"으로 바뀌고, GP에서 결성하면 LP ERP에 약정이 자동으로 들어와 선정 조건과 비교된다
3. GP에서 캐피탈콜을 보내면 LP ERP에 자동으로 들어오고 → 납입 결재 → 납입 기록 → GP 원장과 일치 확인. 금액을 틀리게 입력하면 불일치로 표시된다
4. GP 총회 안건에 LP ERP에서 내부 검토·결재 후 투표하면 GP 화면에 "LP 직접" 투표로 보인다
5. 수기 조합과 연동 조합이 섞여 있어도 포트폴리오 전체의 TVPI·DPI·IRR이 한 화면에 계산된다
6. 조합이 청산되면 최종 성과가 고정되고, 모든 숫자가 대시보드와 일치한다
7. 다른 기관으로 로그인하면 위 데이터가 하나도 보이지 않는다
