## 1. R3에서 보여줄 것

R3가 끝나면 아래 흐름이 **사람이 옮겨 적지 않고** 두 시스템 사이에서 이어진다 (01 7장 성공 기준 2).

```
GP: 출자 제안 발송 ──웹훅──→ LP: 개별 제안 자동 접수 (조합·제안 자동 생성)
LP: 서류 심사 시작  ──API──→ GP: 제안 "검토 중"
LP: 선정 결재 승인  ──API──→ GP: 제안 "확약" (확약 금액, "LP 직접" 표시)
GP: 조합 결성       ──웹훅──→ LP: 결성·약정 원장 사본 → 선정 조건과 자동 비교 → 결성 확인 → 출자 건 활성
```

- 탈락시키면 GP 제안이 "거절"로 바뀐다
- 웹훅을 놓쳐도 "놓친 이벤트 가져오기"로 메워진다
- 수기 조합도 같은 결성 확인 화면을 쓴다 (값만 담당자가 입력)

## 3. 단계별 계획 (7단계, 순서대로)

각 단계가 끝날 때마다 검수 요청을 드린다.

### R3-1. GP에 연동 API 추가 (GP 저장소, D45) — ✅ 2026-10-01 구현

| 할 일 | 내용 |
|---|---|
| 마이그레이션 | GP `lp_proposals` 에 `decided_via` (`gp` / `lp_system`) 추가 |
| 새 API ① | `GET /api/lp/v1/lps/{lp_id}/proposals` — 내 출자 제안 + 검토에 필요한 조합 정보 (LP 05 5-1) |
| 새 API ② | `PUT /api/lp/v1/lps/{lp_id}/proposals/{id}/response` — `reviewing` / `committed` / `declined`. 다시 보내도 결과가 같다 (LP 05 5-2) |
| 기존 API 보완 ③ | 보고 응답에 `my.nav_amount`, `is_correction` (L8). R3에서는 쓰지 않지만 GP 쪽 작업을 한 번에 끝낸다 |
| 기존 API 보완 ④ | 조합 정보 `terms` 에 `primary_purpose_min_ratio`, 운용 인력 지정·교체 때 `fund.updated` 이벤트 |
| GP 화면 | 출자 제안 목록에 "LP 직접" 표시 |
| 바로 보내기 (L20) | 이벤트를 기록한 요청이 끝나면 `after()` 로 웹훅 보내기 시작. 실패하면 지금처럼 주기 작업이 다시 보냄 (GP D46) |
| 문서 | GP 05 5-2, 99 D45를 "구현 완료"로, D46 추가, 00 요약 갱신 |

**검수 방법**: curl로 4가지 호출, GP 화면에서 "LP 직접" 표시 확인.

### R3-2. LP 쪽 연동 설정 (`npm run gp:link`) — ✅ 2026-10-01 구현

연동 설정은 기관이 아니라 서비스 운영자가 하는 일이라 화면 없이 스크립트로 넣는다 (05 3-13).

| 할 일 | 내용 |
|---|---|
| 환경 변수 (LP) | `GP_DEMO_API_KEY` (= GP의 `LP_SYSTEM_API_KEY`), `GP_DEMO_WEBHOOK_SECRET` (= GP의 `LP_WEBHOOK_SECRET`) |
| GP 주소 (L21) | 키처럼 **주소도 환경 변수 이름**으로 저장 (`gp_connections.base_url` → `base_url_env`, 예: `GP_DEMO_BASE_URL`). 같은 DB 행이 로컬(`localhost:3000`)과 배포(`vc-erp-gp.vercel.app`)에서 각자 맞는 GP를 부른다 |
| 스크립트 | `npm run gp:link -- --org a --gp-lp-id <GP 출자자 ID>` <br>① `gp_connections` 한 줄 (없으면) ② 그 기관의 운용사 목록에 연동 GP 한 줄 (`gp_connection_id` 채움) ③ `gp_lp_links` 연결 ④ GP의 `GET /lps/{lp_id}` 를 불러 키·ID가 맞는지 확인 |
| GP 호출 함수 | `lib/gp/client.ts` — 기관 ID만 받고 `gp_lp_id` 는 스스로 꺼낸다. 10초 제한, 실패는 `GP_UNAVAILABLE`, 호출마다 감사 로그 (L16) |
| 환경 변수 (GP) | `LP_SYSTEM_WEBHOOK_URL = http://localhost:3200/api/webhooks/gp/{connection_id}` → **R3-3에서 넣는다**. 받는 주소가 생기기 전에 넣으면 GP에 쌓인 대기 이벤트가 모두 실패로 기록된다 |

**검수 방법**: 기관 A·B 각각 연결 → 스크립트가 "연결 확인됨, GP 출자자: 하늘연금" 처럼 출력. 같은 GP 출자자를 다른 기관에 또 연결하면 DB가 막는 것 확인.

### R3-3. 이벤트 받기 — 웹훅 인박스 + 놓친 이벤트 가져오기

| 할 일 | 내용 |
|---|---|
| 웹훅 주소 | `POST /api/webhooks/gp/{connection_id}` — 서명 확인 → 5분 이내 → `inbound_events` 저장 → 바로 200 (BR-SYNC-01~03, 05 4-3) |
| 가져오기 | `GET /events?after=` 로 빠진 이벤트를 같은 인박스에 (`received_via = pull`) (BR-SYNC-08) |
| 주기 작업 | `GET /api/cron/sync` (`CRON_SECRET`, `scheduled_jobs` 실행 잠금). 하루 1회 ⚠️ |
| 관리자 화면 | `/integration` — 연결 정보(`gp_lp_id` 앞 8자리), 받은 이벤트 현황(받음·처리·실패·무시), "지금 가져오기" 버튼 |
| API | `GET /integration`, `GET /integration/events`, `POST /integration/pull` |

이 단계에서는 **받아서 쌓기만** 한다. 처리는 R3-4.

**검수 방법**: GP에서 이벤트 발생 → LP 관리자 화면에 "받음"으로 보임. 서명을 틀리게 보내면 401이고 저장 안 됨. 같은 이벤트 두 번 → 한 번만 저장.

### R3-4. 받은 이벤트 처리 (동기화)

이벤트 본문으로 데이터를 만들지 않고, **GP API로 다시 읽어서** 반영한다 (BR-SYNC-05).

| GP 이벤트 | R3에서 하는 것 |
|---|---|
| `fund.status_changed`, `fund.updated`, `fund.terms_updated` | 연동 조합 정보 갱신 (상태·결성일·결성액·기간·보수·의무 비율), `last_synced_at` |
| `member.joined` | 조합 정보 + 원장 다시 읽기 → 결성 확인 대상 표시 |
| `ledger.entry_created` | `gp_ledger_entries` 에 새 행 (모든 구분 저장). **대사는 약정만** — 납입·분배 대사는 우리 장부에 납입·분배가 생기는 R4·R6부터 |
| `notice.sent` 중 출자 제안 통지 | R3-5 |
| 그 밖의 통지(캐피탈콜·분배·총회·보고), `meeting.result_finalized` | `ignored` + 사유 "R3 미지원" (L22). 해당 릴리스에서 "GP와 다시 맞추기"로 채운다 |

| 할 일 | 내용 |
|---|---|
| 처리 순서 | 연결별 발생 순서. 앞 이벤트가 실패하면 같은 기관·조합의 뒤 이벤트는 기다린다 (BR-SYNC-04) |
| 기관 찾기 | `gp_lp_id` → `gp_lp_links`. 조합 전체 이벤트는 그 조합을 가진 모든 기관. 못 찾으면 `ignored` (BR-SYNC-06) |
| 실패 | `failed` + 다음 시도 시각, 5번까지 (BR-SYNC-07). 관리자 화면 "다시 처리" 버튼 |
| 처리 시작 | 웹훅 응답 후 `after()` 로 바로 + 주기 작업이 안전망 (L15) |
| 다시 맞추기 | 조합 화면 "GP와 다시 맞추기" — 그 조합의 GP API를 전부 다시 읽기 (BR-SYNC-09) |
| 연결 직후 첫 맞추기 | R3-2 스크립트 끝에 이 기관의 GP 조합·제안을 전부 읽고, 이벤트 위치를 GP 최신으로 맞춘다 (과거 이벤트를 하나씩 다시 처리하지 않음) |

**검수 방법**: GP에서 조합 정보를 고치면 LP 조합 화면에 반영. 처리 중 GP를 꺼 두면 `failed` → 켜고 "다시 처리" → `processed`. 같은 이벤트를 두 번 처리해도 사본이 늘지 않음.

### R3-5. 연동 제안 자동 접수 + GP에 응답 보내기

| 할 일 | 내용 |
|---|---|
| 자동 접수 | 출자 제안 통지 → GP `GET /lps/{lp}/proposals` → 연동 조합(`fundraising`) + 제안(`direct`, `gp_api`, 요청액 = GP 제안 금액) 생성. 이미 있으면 갱신만 (BR-PROP-03) |
| 공고 부문 지정 | 연동 제안을 담당자가 공고 부문에 붙일 수 있다 (접수 기간 검사 안 함) ⚠️ |
| 응답 보내기 | `received` 에서 처음 다음 단계로 → `reviewing`, 선정 결재 승인 → `committed` (확약 금액 = 출자 예정액), 탈락 → `declined` (BR-PROP-06). **LP 저장이 끝난 뒤** 보낸다 |
| 못 보낸 것 | `gp_response_sent_at` 이 비어 있으면 보낼 것 (BR-SYNC-11). 주기 작업 + 제안 화면 "GP에 다시 보내기" + 관리자 화면 "못 보낸 것 지금 보내기" |
| GP가 거부 | (예: GP에서 이미 거절됨) LP 상태는 되돌리지 않고 제안 화면·관리자 화면에 경고 ⚠️ |
| 철회 | 연동 제안은 철회 불가 → 탈락으로 처리 (BR-PROP-05) |
| 화면 | 제안 목록·상세에 "GP 연동" 표시, GP 응답 상태(보냄 / 보내지 못함 + 시각) |
| API | `POST /proposals/{id}/gp-response/resend`, `POST /integration/send-pending` |

**검수 방법**: 기관 A로 '딥테크 스케일업 투자조합' 제안 자동 접수 확인 → 서류 심사 → GP 화면 "검토 중" → 선정 조건·결재 → GP 화면 "확약 30억, LP 직접". 기관 B는 탈락 → GP "거절".

### R3-6. 결성 확인 · 약정 장부

| 할 일 | 내용 |
|---|---|
| 결성 확인표 | `GET /commitments/{id}/formation-check` — 조합 결성 여부, 결성일 ≤ 결성 기한, 결성액 ≥ 최소 결성 규모, 약정 ÷ 결성액 ≤ 출자 비율 상한, 약정 ≤ 출자 예정액 (BR-CMT-02) |
| 결성 확인 | `POST /commitments/{id}/confirm` 💰 — 연동은 GP 값(원장 사본의 약정 합계), 수기는 입력값. 우리 장부 `commitment` 행 + 대사 (BR-CMT-03, 04) |
| 선정 취소 | `POST /commitments/{id}/cancel` — 결성 대기에서만, 사유 필수. 결성 기한이 지나도 자동 취소 안 함 (BR-CMT-05) |
| 약정 변경 | `POST /commitments/{id}/commitment-adjustments` 💰 — 취소 행 + 새 행 (BR-CMT-06) |
| 장부 보기 | `GET /commitments/{id}/ledger` — 우리 장부와 GP 원장 사본 나란히 + 대사 상태 |
| 화면 | `/commitments` 출자 건 목록(상태·약정액·대사), `/commitments/[id]` 상세(결성 확인표, 확인 버튼, 장부 나란히 보기, 대사 이력). 대사 불일치 확인 메모(BR-REC-05)도 여기서 |
| 가져온 출자 건 (L19) | 연동 첫 맞추기·다시 맞추기에서 **GP 약정이 이미 있는 조합**은 제안 없이 출자 건(`origin = imported`)을 만들고 GP 약정으로 결성 확인까지 한다. 결성 확인표의 기한·비율·예정액 검사는 "해당 없음" (선정 조건이 없으므로). 마이그레이션 `002`: `commitments.proposal_id` 비울 수 있게 + `origin` |

**검수 방법**: ⓪ 'LP연동 데모 벤처투자조합'이 두 기관에 "가져온 출자 건"(활성, 약정 일치)으로 보임 ① GP에서 '딥테크' 조합 결성 → LP 출자 건에 결성 확인표가 자동으로 채워짐 → 확인 → 활성, 장부 약정 = GP 약정 "일치" ② GP가 확약보다 큰 금액으로 결성하면 확인 불가 ③ 기관 A 한결(수기) 결성 확인 ④ 다른 기관으로 로그인하면 안 보임.

### R3-7. LP 배포 + 배포 환경끼리 연결 (L21)

| 할 일 | 내용 |
|---|---|
| LP 배포 | Vercel `vc-erp-lp`, 서버 지역 싱가포르(`sin1`, GP와 같은 이유), 로딩 화면. 원래 R7이던 배포를 앞당긴다 |
| LP 데모 DB (L23) | Neon 브랜치 `demo-seed`·`demo`, 배포 LP는 `demo` 를 쓴다. 매일 03:00 KST에 GP와 함께 되돌린다. `npm run db:demo-refresh` (LP) + "GP 먼저 → LP" 짝 맞춘 갱신 절차. **LP용 Neon API 키는 사용자가 발급** |
| 환경 변수 (LP 배포) | `GP_DEMO_BASE_URL = https://vc-erp-gp.vercel.app/api/lp/v1`, `GP_DEMO_API_KEY`, `GP_DEMO_WEBHOOK_SECRET`, `CRON_SECRET` |
| 환경 변수 (GP 배포) | `LP_SYSTEM_WEBHOOK_URL = https://vc-erp-lp.vercel.app/api/webhooks/gp/{connection_id}` (지금은 비어 있음) |
| 주기 작업 | LP `/api/cron/sync` 하루 1회, `/api/cron/reset-demo` 매일 03:00 KST (L23) |
| 접근 | 배포 보호(Vercel 로그인 요구)가 꺼져 있어야 GP 웹훅이 들어온다. GP 설정과 맞춘다 |

**검수 방법**: 배포 GP에서 출자 제안·결성 → 배포 LP에 자동으로 들어옴. 배포 LP에서 선정 → 배포 GP 화면 "확약, LP 직접". 다음 날 초기화 뒤에도 연동이 이어지는지 확인.

## 4. R3에서 하지 않는 것

## 6. 정했던 것 — Q5 (A로 확정, L23)

### Q5. GP 데모 DB가 매일 초기화되는 문제를 어떻게 풀까?

배포 GP는 매일 03:00에 `demo-seed` 상태로 되돌아간다. 그때 LP 배포 DB는 그대로면 이렇게 깨진다.

1. **이벤트를 더 못 받는다**: LP가 기억하는 "마지막으로 받은 GP 이벤트"가 GP에서 사라진다. GP의 `GET /events?after=` 는 모르는 이벤트 ID를 받으면 **빈 목록**을 돌려준다 (GP 코드 확인). 그 뒤로 놓친 이벤트 가져오기가 영원히 아무것도 못 가져온다
2. **두 시스템 숫자가 어긋난다**: 면접관이 LP에서 '딥테크' 제안을 선정해 GP가 "확약"이 됐다면, 다음 날 GP는 "제안" 상태로 돌아가지만 LP는 "선정"으로 남는다. 그 뒤 GP에서 다시 제안·결성하면 LP 쪽 상태와 맞지 않아 오류가 난다

- **A. LP도 똑같이 매일 초기화하고, 두 스냅샷의 짝을 맞춘다 (기본안)**
  - LP에도 Neon 브랜치 `demo-seed`·`demo` 를 두고 같은 03:00에 되돌린다 (GP D44와 같은 방식)
  - 두 `demo-seed` 는 **연결·첫 맞추기가 끝난 로컬 개발 DB끼리**를 한꺼번에 복사해 만든다 → 되돌아간 뒤에도 LP가 기억하는 이벤트·제안 상태가 GP와 정확히 같다
  - `npm run db:demo-refresh` 를 LP에도 만들고, "GP 먼저 → LP" 순서로 함께 돌리는 절차를 문서에 남긴다
  - 덤으로 LP 데모도 면접관이 마음껏 눌러 볼 수 있게 된다 (원래 R7에서 필요했던 일)
  - 비용: 무료. 할 일: LP용 Neon API 키를 **직접 발급**해 주셔야 한다 (GP 때처럼 이 프로젝트 전용 키)
- B. LP는 초기화하지 않고 GP 초기화를 알아채서 따라 맞춘다
  - GP가 "초기화됨" 신호를 보내거나, LP가 이벤트 위치가 사라진 것을 보고 연동 데이터를 전부 다시 맞춘다
  - LP의 심사·결재 기록은 남는데 GP 쪽만 되돌아가므로, "LP는 선정, GP는 제안" 같은 어긋남을 정리하는 규칙이 많이 필요하다. 면접관이 남긴 데이터도 계속 쌓인다
- C. 배포 GP의 매일 초기화를 끈다
  - 가장 간단하지만 GP D44(면접관이 마음껏 눌러 보게)를 되돌리는 것이라 권하지 않는다
