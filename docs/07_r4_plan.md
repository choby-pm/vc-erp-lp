## 1. R4에서 보여줄 것

R4가 끝나면 **돈이 나가는 흐름**이 결재를 거쳐 장부에 남고, GP 숫자와 자동으로 맞춰진다 (01 7장 성공 기준 3).

```
GP: 캐피탈콜 발송     ──웹훅──→ LP: 캐피탈콜 자동 수신 (회차·요청액·납입 기한)
LP: 납입 기안         ──────→ 결재권자 승인 (L4)
LP: 송금 완료 기록    ──────→ 우리 장부 '납입' 행 + 대사 (GP 확인 전이라 "확인 대기")
GP: 입금 확인 기록    ──웹훅──→ LP: GP 원장 사본 '납입' 행 → 대사 "일치"
```

- 결재 없이 송금 기록 불가, 요청액·남은 약정을 넘는 납입 차단
- 금액을 틀리게 기록하면 "불일치" → 정정(취소 행) 또는 확인 메모
- 자금 계획: 앞으로 몇 월에 얼마가 필요할지 (확정된 요청 + 추정)
- 수기 조합(한결)도 같은 화면에서 캐피탈콜을 입력해 같은 흐름

## 2. 지금 상태 (2026-10-03 확인)

| 항목 | 상태 |
|---|---|
| DB | `capital_calls`, `payments`, 뷰 `v_capital_call_status`·`v_commitment_summary`·`v_cashflows` 가 R0 스키마에 **이미 있다** (비어 있음). 결재 대상에 `payment` 도 이미 있다 |
| 결재 | 선정 결재만 구현 (`approve()` 가 `payment` 면 "아직 지원하지 않음") |
| 연동 | GP `GET …/funds/{f}/capital-calls` (회차·내 요청액·내 납입액·GP가 본 납입 상태). 웹훅 `notice.sent`(capital_call) · `ledger.entry_created`(contribution) 는 지금 "R4에서 처리"로 **무시** 중 (L22) |
| GP 동작 | 캐피탈콜은 초안 → 발송 → 마감. **발송한 캐피탈콜을 취소하는 기능이 없다** (초안만 삭제). LP 납입은 GP 담당자가 은행 입금을 보고 GP에 기록 → 원장 행 |
| 데모 데이터 | 'LP연동 데모 벤처투자조합': GP 캐피탈콜 1~3회 **모두 납입 완료**, 분배 1회 (GP 원장: 하늘 납입 30억·분배 10억, 바다 납입 20억·분배 8억). LP 우리 장부에는 납입 0 → 지금 "대사 전" (가져온 출자 건의 과거 기록, Q1). **R4 흐름을 보여줄 미납 캐피탈콜이 없다** (Q4) |
| 수기 | 한결 초기 1호: 결성 대기 (데모 시작 상태) |

## 3. 단계별 계획 (5단계, 순서대로)

각 단계가 끝날 때마다 검수 요청을 드린다.

### R4-1. 캐피탈콜 수신 · 수기 등록 · 목록

| 할 일 | 내용 |
|---|---|
| 마이그레이션 006 | `payments.origin` (`approval` 결재를 거친 납입 / `imported` 가져온 납입, L27), `capital_calls.gp_paid_amount` (GP가 본 우리 납입액 → "우리는 보냈는데 GP는 미납" 찾기) |
| 연동 수신 | `notice.sent`(capital_call) → GP 캐피탈콜 목록을 다시 읽어 회차별로 만들기·갱신 (요청액 = 내 요청액, 기한, GP가 본 납입 상태). 조합 "GP와 다시 맞추기"·첫 맞추기도 캐피탈콜까지 읽는다 |
| 약정 초과 요청 | 연동은 GP가 원본이라 받아들이되 표시 (BR-CALL-03). 주의 목록 연결은 R5 |
| 수기 등록·취소 | 활성 출자 건만 (BR-CMT-07). 회차 유일, 기한 ≥ 요청일, 요청액 ≤ 남은 약정 (BR-CALL-02·03). 취소는 송금한 납입이 없을 때만 (BR-CALL-04) |
| 화면 | `/capital-calls` 전체 목록(미납·기한 경과·전체), 출자 건 상세에 캐피탈콜 표 |

> R4-1 구현 (2026-10-03): 마이그레이션 006 적용. `lib/services/capital-calls.ts`, `syncCalls`(조합 맞추기에 포함), 캐피탈콜 통지 웹훅 처리, 수기 등록·취소, `/capital-calls` 화면, 출자 건 상세 캐피탈콜 표
> 검수: 'LP연동' 1~3회 수신(다시 맞춰도 늘지 않음), GP 4회 발송 → 웹훅으로 자동 수신(하늘 5억·바다 4억), 한결 결성 확인 + 수기 1회 20억 (남은 약정 초과·중복 회차·결성 전·연동 조합·권한·다른 기관 차단). **로컬 데모 상태**: GP 'LP연동' 4회 발송(L30), 한결 결성 + 수기 1회 — R4-5에서 GP 시드 스크립트에도 반영

### R4-2. 납입 기안 · 결재 · 송금 완료 · 정정

| 할 일 | 내용 |
|---|---|
| 납입 기안 | `POST /capital-calls/{id}/payments` — 금액 ≤ 요청액 − (송금 완료 + 결재 대기 + 송금 대기) (BR-PAY-02, L9 분할 납입). 만들면 바로 결재 기안 |
| 결재 | 기존 결재함에 "납입" 추가. 승인 → 송금 대기, 반려 → 반려 (BR-APR) |
| 송금 완료 | `POST /payments/{id}/mark-paid` — 승인된 것만 (BR-PAY-03). 송금일·이체 번호. 한 트랜잭션: 납입 완료 + 우리 장부 '납입' 행 + 대사 (BR-PAY-04) |
| 취소·정정 | 결재 대기·송금 대기는 취소. 송금 완료를 잘못 기록했으면 **원래 날짜**로 취소 행 + 대사 (BR-PAY-05) |
| 연동 반영 | `ledger.entry_created`(contribution) → GP 원장 사본 + 납입 대사 (지금은 약정만 대사함) |
| 화면 | 캐피탈콜 상세(납입 목록·기안·송금 기록), 결재함에 납입 결재 |

> R4-2 구현 (2026-10-03): `lib/services/payments.ts`, 결재(승인 → 송금 대기, 반려 → 반려), 캐피탈콜 상세 화면(기안·송금 기록·정정), 결재 상세에 납입 화면, 납입 대사(동기화에서도). L31
> 검수: 한도 초과·분할·결재 전 취소/송금 차단·승인·반려·송금일 검사·송금 완료(장부+대사, 확인 대기)·정정(원래 날짜 취소 행)·수기 납입(대사 대상 아님)·캐피탈콜 취소와의 관계·같은 키 두 번·다른 기관. GP 입금 기록 → "일치"는 R4-3(과거 납입) 뒤 배포에서 확인 (로컬 GP 원장은 지울 수 없어서)

### R4-3. 가져온 출자 건의 과거 납입 (Q1)

이 시스템 전에 이미 출자한 조합(L19)의 과거 캐피탈콜·납입을 우리 장부로 옮긴다 (L27). 첫 맞추기·다시 맞추기에서 GP 원장의 과거 납입 행마다 **가져온 납입**(결재 없음, `origin = imported`, 근거 = GP 원장 행)을 만들고 우리 장부 '납입' 행 + 대사. 화면에 "가져온 납입" 표시. 분배는 R6에서 같은 방식

> R4-3 구현 (2026-10-03): 마이그레이션 007(`payments.gp_entry_id`), `lib/services/imported-payments.ts`, 조합 맞추기 끝에서 실행. L32
> 검수: 하늘 3건 30억·바다 3건 20억 옮김 → 납입 대사 "일치", 캐피탈콜 상태가 GP와 같아짐(바다 3회 8억 중 4억, 기한 경과), 다시 맞춰도 늘지 않음, 4회(연결 뒤)는 미납 그대로, 가져온 납입 정정 차단. 가져온 출자 건 약정 날짜를 GP 명부 확정일로 바로잡음

## 4. 정할 것

### Q1. 가져온 출자 건의 과거 납입 (L19에서 R4로 미룬 것)

지금 'LP연동' 조합은 GP 원장에 납입·분배가 있는데(하늘 30억·10억, 바다 20억·8억) 우리 장부는 0이라 "대사 전"이다.

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (추천)** | 첫 맞추기 때 GP의 과거 캐피탈콜을 우리 캐피탈콜로 만들고, GP 원장의 과거 납입을 **"가져온 납입"**(결재 없음, 근거 = GP 원장)으로 우리 장부에 옮긴다. 분배는 R6에서 같은 방식 | 장부가 처음부터 GP와 맞고, 성과 계산(R6)에 과거 현금흐름이 들어간다 | "결재 없는 납입"이라는 예외가 생긴다 (가져온 출자 건에만, 화면에 표시) |
| B | 대사를 "연결 이후 기록"만 비교한다 (기준일 이전은 제외) | 예외 납입이 없다 | 우리 장부의 납입 합계·남은 약정이 틀린 채로 남고, 성과 계산이 안 된다 |
| C | 그대로 두고 담당자가 불일치 확인 메모 | 할 일 없음 | 남은 약정·자금 계획·성과가 모두 틀린다 |

### Q2. LP 송금을 GP에 알릴까?

LP가 송금 완료를 기록해도 GP는 모른다. GP 담당자가 은행 입금을 보고 GP에 따로 기록해야 원장에 들어온다 (그 사이 7일은 "확인 대기").

| 선택지 | 내용 |
|---|---|
| **A (추천)** | 알리지 않는다. 실제 업무도 GP가 은행 입금을 확인하고 기록한다. 데모에서는 GP 화면에서 입금을 기록해 "일치"를 보여준다 |
| B | GP에 "LP 송금 알림" API를 추가해(GP D47) GP 화면에 "LP가 ○월 ○일 송금했다고 알림"을 띄운다. 입금 기록은 여전히 GP 담당자 |

### Q3. 자금 계획 계산 방식 ⚠️ 단순화

| 선택지 | 내용 |
|---|---|
| **A (추천)** | ① 받은 캐피탈콜 중 아직 안 낸 금액은 **납입 기한이 있는 달에 "확정"** ② 나머지 남은 약정은 투자 기간 끝까지 **매달 똑같이 나눠 "추정"** ③ 투자 기간이 끝난 조합의 남은 약정은 추정하지 않고 "투자 기간 이후 잔여"로 따로 표시 (관리보수·후속 투자용으로만 요청되므로) |
| B | 05 API 설계 그대로: 남은 약정 ÷ 남은 투자 기간 월수 (확정 구분 없음) |

### Q4. R4 시연용 데모 데이터

GP 데모 조합의 캐피탈콜은 모두 납입 완료라 R4 흐름을 보여줄 것이 없다.

| 선택지 | 내용 |
|---|---|
| **A (추천)** | GP 개발 DB에서 'LP연동' 조합에 **4회 캐피탈콜을 발송만 한 상태**로 만들어 데모에 넣는다 (GP 저장소 시드 스크립트에 추가). 면접관은 LP에서 바로 기안 → 승인 → 송금 기록, GP에서 입금 기록을 해 볼 수 있다. LP 한결은 결성·수기 캐피탈콜까지 해 둔다 |
| B | 데모 데이터는 그대로. 면접관이 GP에서 캐피탈콜을 직접 발송해야 시작된다 |

## 5. R4에서 하지 않는 것

- 주의 목록(납입 기한 임박·대사 불일치 7일 경과) 화면 → R5. R4는 목록 화면의 표시까지
- 분배 수령·과거 분배 옮기기 → R6 (Q1 A면 같은 방식)
- 은행 연동 자동 송금, 송금 확인서 첨부 → 고도화
- GP에 캐피탈콜 취소가 없으므로, 연동 캐피탈콜 취소(BR-CALL-04 연동 부분)는 GP가 기능을 만들 때까지 처리하지 않는다 ⚠️
