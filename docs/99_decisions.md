# 99. 결정 기록

설계 중 내린 결정과 그 이유를 남긴다. 결정이 바뀌면 지우지 않고 새 번호로 추가한다.
GP 시스템의 결정(D 번호)과 구분하려고 **L 번호**를 쓴다.

---

## L1. LP 시스템은 LP 기관용 ERP (2026-09-29 확정)

- **결정**: LP 시스템을 "조합원이 GP 데이터를 보는 포털"이 아니라, 출자기관이 **여러 GP의 여러 조합**에 한 출자를 관리하는 ERP로 만든다. 우리 GP 시스템은 연결된 GP 중 한 곳이다.
- **검토한 선택지**
  - LP 포털: GP 연동 API를 거의 그대로 쓰면 돼 빠르지만, 출자기관 업무(심사·결재·자금 계획·성과 분석)를 보여줄 수 없다
  - **LP 기관용 ERP (채택)**: 범위는 크지만 LPworks 같은 출자기관 서비스와 직접 맞닿는다. 포털 기능(내 GP 데이터 보기)은 그 안에 포함된다
- **따라오는 것**: 연동되지 않은 GP의 조합은 수기로 입력해야 한다 → 연동·수기 데이터를 같은 구조로 다룬다 (01 5-3)

## L2. 여러 기관이 쓰는 서비스(SaaS), 기관별 데이터 분리 (2026-09-29 확정)

- **결정**: 여러 출자기관이 한 시스템을 함께 쓰고, 기관마다 데이터를 완전히 분리한다. 기관이 만든 모든 데이터에 `org_id` 를 붙이고, 서버 한 곳에서 로그인한 사용자의 기관으로 거른다. 다른 기관 데이터 ID로 요청하면 `404`.
- **검토한 선택지**
  - 기관 한 곳 전용: 단순하지만 서비스(SaaS) 설계 경험이 드러나지 않는다
  - 기관마다 DB를 따로: 분리는 가장 확실하지만 무료 요금제에서 DB 개수·마이그레이션 관리 부담이 크다
  - **한 DB + 기관 ID로 분리 (채택)**: 대부분의 B2B 서비스 방식. 거르는 검사를 빠뜨리면 데이터가 새므로 검사 위치를 한 곳으로 모은다
- **데모**: 기관 2곳을 넣어 서로 안 보이는 것을 보여준다

## L3. 출자 방식: 공고형 · 개별 제안형 모두 (2026-09-29 확정)

- **결정**: 정책 출자기관의 **출자사업 공고** 방식과 연기금·금융기관의 **개별 제안** 방식을 모두 지원한다. 둘 다 "출자 제안" 한 건으로 통일해 같은 심사·선정 흐름을 탄다. 공고를 통해 들어왔는지만 구분한다.
- **검토한 선택지**: 공고형만 (심사 절차는 풍부하지만 연동 GP의 개별 제안을 받을 곳이 없다), 개별 제안형만 (단순하지만 정책 출자기관 업무가 빠진다)
- **이유**: 연동 GP의 출자 제안 통지가 자연스럽게 개별 제안으로 들어온다

## L4. 내부 결재: 출자 선정 · 납입 · 총회 투표 (2026-09-29 확정)

- **결정**: 기안 → 결재 대기 → 승인 / 반려 흐름을 세 곳에 건다. 기안자는 자기 건을 결재할 수 없다. MVP는 결재자 한 명.
- **검토한 선택지**: 결재 없이 역할 권한으로만 막기 (빠르지만 "승인받고 돈을 보낸다"는 기관 업무의 핵심이 빠진다), 모든 업무에 결재 (범위가 너무 커진다)
- **한계** ⚠️: 여러 단계 결재선, 전결 규정(금액별 결재권자)은 고도화로 미룬다

## L5. GP 시스템에 API 추가 허용 (2026-09-29 확정)

- **결정**: 양방향 연동에 필요한 만큼 GP 시스템(`vc-erp/gp`)에도 API를 추가한다. 첫 대상은 **출자 제안 응답**(LP가 확약 금액 또는 거절을 보내면 GP의 출자 제안 상태가 바뀜).
- **검토한 선택지**: GP는 그대로 두고 기존 13개 API만 쓰기 (출자 제안 응답을 GP 담당자가 직접 옮겨 적어야 한다)
- **원칙**: GP에 추가하는 API도 GP의 기존 규칙(API 키 인증, 공개 등급, 멱등성 키, 감사 로그)을 따른다. GP 문서(05 API 설계, 99 결정 기록)에도 D 번호로 함께 남긴다

## L6. 연동 조합의 GP 데이터는 LP DB에 읽기 전용 사본으로 저장 (2026-09-29 확정)

- **결정**: 웹훅과 이벤트 다시 받기로 들어온 GP 데이터를 LP DB에 사본으로 저장한다. LP ERP에서는 고치지 않는다. 우리 장부와 나란히 두고 대사한다.
- **GP D2와의 관계**: D2는 "복제를 최소화한다"였지만, 그때 가정한 LP 시스템은 한 GP의 데이터만 보는 포털이었다. LP ERP는 **여러 GP를 모아 성과를 계산하고, 우리 장부와 맞춰봐야** 하므로 사본이 필요하다. GP DB가 원본이라는 원칙은 그대로다 (사본이 GP와 다르면 GP가 맞다).
- **검토한 선택지**: 볼 때마다 GP API 호출 (사본 관리는 없지만 연동 GP가 여러 곳이면 느리고, GP가 멈추면 화면도 멈추고, 수기 조합과 한 번에 계산할 수 없다)
- **따라오는 것**: 받은 이벤트 기록(중복 거르기·순서·실패 처리)과, 사본이 GP 최신 상태와 맞는지 다시 맞추는 방법이 필요하다 (R3에서 설계)

## L7. DB 행 단위 보안(RLS)은 고도화로 (2026-09-29 확정)

- **결정**: 기관 분리는 ① 서버 한 곳(`withOrg`)에서 로그인한 사용자의 기관 ID로 거르기 ② 복합 외래 키로 기관이 다른 행끼리 연결 금지, 두 겹으로 막는다. RLS는 MVP에 넣지 않는다.
- **검토한 선택지**: MVP에 RLS 넣기 — 서버가 검사를 빠뜨려도 DB가 다른 기관 행을 돌려주지 않아 가장 안전하다. 하지만 모든 쿼리를 트랜잭션 안에서 기관 ID를 설정한 뒤 실행해야 하고, Neon 커넥션 풀러(pgbouncer, 트랜잭션 모드)와 함께 쓸 때 설정이 까다롭다.
- **한계** ⚠️: 서버 코드가 조회에서 기관 조건을 빠뜨리면 다른 기관 데이터가 **읽힐 수는** 있다 (연결은 DB가 막는다). 그래서 기관 조건을 개별 쿼리에 맡기지 않고 서비스 함수가 항상 `org_id` 를 첫 인자로 받게 하고, 기관 2곳 데모 데이터로 분리 테스트를 한다.

## L8. 연동 조합의 우리 몫 평가액은 GP가 계산해서 준다 (2026-09-29 확정)

- **배경**: GP 정기 보고 스냅샷에는 조합 전체 숫자만 있고 LP별 평가액이 없다 (GP 코드 확인). 성과 지표(TVPI·RVPI·IRR)에는 우리 몫 평가액이 필요하다.
- **결정**: GP 연동 API의 보고 응답에 우리 몫 평가액을 추가한다 (L5 범위, 계산 방식은 GP 문서에 D 번호로 남긴다). 수기 조합은 담당자가 보고서의 숫자를 입력한다.
- **검토한 선택지**: LP ERP가 "조합 전체 평가액 × 우리 지분율"로 직접 계산 — GP 변경은 없지만, 계산 책임이 원본이 아닌 곳에 생기고 실무에서는 LP별 평가액이 지분율과 정확히 비례하지 않을 수 있다 ⚠️

## L9. 분할 납입 허용 (2026-09-29 확정)

- **결정**: 캐피탈콜 한 건에 납입(`payments`)을 여러 건 기록할 수 있다. 납입 합계는 요청액을 넘을 수 없다.
- **이유**: 자금 사정이나 내부 결재 한도 때문에 나눠 보내는 경우가 있다. GP도 일부 납입(`partial`) 상태를 이미 다룬다.

## L10~L12. 비즈니스 규칙 세부 (2026-09-29 확정)

- **L10 대사 확인 대기 7일**: 불일치가 생긴 지 7일(달력일) 안이면 "확인 대기"로만 표시하고 주의 목록에 올리지 않는다. 송금일과 GP 입금 확인일이 다른 것은 정상이기 때문. 영업일 계산은 공휴일 달력이 필요해 고도화 ⚠️
- **L11 보고 기한 = 분기 말 + 45일**: 결성 확인된 출자 건의 조합은 분기마다 보고가 있어야 한다고 가정. 조합별 보고 주기·기한 입력은 고도화 ⚠️
- **L12 관리자는 결재권자를 겸한다**: 작은 기관·데모에서 결재자가 없어 막히지 않게. 본인 결재 금지(BR-APR-05)는 그대로
- **함께 확정**: 수기 조합은 대사하지 않고 "대사 대상 아님"으로 표시 (BR-REC-07)

## L13~L17. API 설계 (2026-09-29 확정)

- **L13 공통 규칙은 GP와 같다**: REST, snake_case, 상태 변경은 동작 API, 돈이 움직이는 요청은 멱등성 키, 금액 검사는 미리보기 API (GP D20~D23, D26)
- **L14 주소에 기관 ID를 넣지 않는다**: 세션의 기관이 곧 범위다. 주소로 받으면 모든 API에서 "주소의 기관 = 세션의 기관"을 검사해야 하고, 한 곳만 빠뜨려도 다른 기관 데이터가 샌다. 아예 받지 않으면 빠뜨릴 검사가 없다
- **L15 웹훅은 저장 후 바로 응답, 처리는 따로**: 서명 확인 → 인박스 저장 → 200. 처리는 Next.js `after()` 로 응답 후 바로 시작하고, 놓친 것은 주기 작업이 메운다. GP의 10초 제한·재전송 규칙(GP BR-EVT-06)에 맞춘다
- **L16 GP 호출은 한 함수(`lib/gp/client.ts`)로만**: 함수가 기관 연결에서 `gp_lp_id` 를 스스로 꺼내고, 호출 코드는 `lp_id` 를 넘길 수 없다. API 키는 환경 변수에서만 읽는다
- **L17 GP 추가 API 4가지**: 제안 목록, 제안 응답(`decided_via`), 보고의 우리 몫 평가액, 의무 비율·운용 인력 변경 이벤트. GP 문서에 D45로 기록 (구현은 R3)
- **함께 확정**: 데모 로그인은 기관 2곳 × 역할 3개(담당·결재권자·관리자) 선택. GP 연동 설정은 화면 없이 설정 스크립트로 넣는다
- **GP 호출의 중복 방지**: GP LP 연동 API에는 멱등성 키가 없다(GP의 키는 로그인 사용자 기준). 그래서 GP로 보내는 요청은 다시 보내도 결과가 같은 형태로 설계했다 (BR-SYNC-12)
