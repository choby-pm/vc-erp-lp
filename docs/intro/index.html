연동

두 시스템 사이에 오가는 것

웹훅은 “무언가 바뀌었다”는 신호로만 씁니다. 받으면 GP API를 다시 읽어 맞추기 때문에, 하나를 놓쳐도 다음 동기화가 바로잡습니다. LP가 GP에 보내는 것은 먼저 저장하고, 못 보내면 표시해 두었다가 다시 보냅니다. GP가 LP를 부르는 것은 공고 게시판 읽기와 공고 지원 두 가지이고, 웹훅과 같은 비밀값으로 서명합니다.

결성 · 원장 기록→ 웹훅GP 원장 사본 갱신 → 약정 대사

배포 사이트에서 따라가는 순서

LP 사이트에 하늘연금으로 들어가 위에서부터 차례로 누르면, 출자 담당이 한 해 동안 하는 일이 처음부터 끝까지 이어집니다. 화면은 2026-10-04 배포 데모에서 찍었습니다. 데모는 매일 03:00(KST)에 처음 상태로 돌아갑니다. 캡처를 누르면 크게 볼 수 있습니다.

0 / 전체 그림

대시보드에서 올해 예산, 포트폴리오, 오늘 할 일을 한 번에

LP · 출자 담당대시보드

말할 것

“예산 170억/500억, 포트폴리오 TVPI 1.13배와 IRR 14.5%, 이번 달 납입 예정이 위에 있고, 아래는 결성 기한·수령 대기 분배·투표할 총회 같은 할 일입니다.”

“이 숫자는 따로 저장하지 않습니다. 예산·성과·자금 계획 화면과 같은 함수로 계산해서, 화면끼리 어긋날 수 없습니다.”

1 / 계획 → 심사 → 선정

GP 세 곳이 제안하고 두 곳이 선정됩니다. 부문 한도를 넘는 선정은 시스템이 막습니다

LP · 출자 담당출자 심사 → 출자사업 “2026년 정기 출자사업”, 탈락한 “미래로 씨앗 2호”

말할 것

“초기 부문 200억에 세 곳이 제안했고, 한결과 새솔이 선정돼 170억을 썼습니다.”

“미래로는 50억을 요청했는데 부문에 30억밖에 안 남아 선정 결재 자체가 올라가지 않았습니다. 막힌 이유가 탈락 사유와 점검표에 그대로 남습니다. 분야 배분 초과는 실무상 전용이 흔해 경고만 띄웁니다.”

2 / 공고에 GP가 지원

기관이 올린 공고에 GP가 조합으로 지원하고, 선정되면 앵커 조건으로 나머지 출자자를 모읍니다

LP출자 심사 → 공고 게시판 · GP출자사업 공고 → 바다 "하반기 성장 출자사업" → 그로스 1호로 지원 · 바다성장출자 심사 · 선정 · GP조합 → 출자 제안

말할 것

“정책 출자기관은 공고를 올리고 GP가 찾아와 지원합니다. 이 서비스를 쓰는 기관들의 공고가 한 게시판에 모이고, 연동된 GP는 GP ERP에서 바로 지원합니다. 조합 분야가 부문 분야와 다르면 지원할 수 없습니다.”

“지원은 LP가 받은 순간으로 접수 기간을 봅니다. 선정되면 결성 기한 · 비율 상한 같은 조건이 GP로 가서, ‘결성액이 200억은 돼야 하고 160억을 더 모아야 한다’가 바로 보입니다. 나머지는 지금처럼 다른 LP에게 개별 제안으로 모읍니다.”

3 / LP 결정이 GP로

LP에서 선정 결재를 승인하면 GP 화면의 출자 제안이 “확약 · LP 직접”으로 바뀝니다

LP · 출자 담당 → 결재권자출자 제안 “딥테크 스케일업” → 선정 결재 올리기 → 결재함에서 승인 · GP딥테크 조합 → 출자 제안

말할 것

“이 제안은 GP 시스템에서 웹훅으로 자동 접수된 것입니다. 승인하는 순간 LP가 GP 응답 API를 불러, GP 쪽에 ‘LP 직접’ 표시가 붙은 확약이 생깁니다. GP 담당자가 대신 입력한 것과 구분됩니다.”

4 / 납입과 대사

GP 캐피탈콜이 자동으로 들어오고, 결재·송금 뒤 GP 원장과 맞춰 봅니다

LP납입·분배 → 캐피탈콜 “LP연동 · 4회” → 납입 기안 → 승인 → 송금 기록 · GP입금 기록

말할 것

“송금을 기록하면 우리 장부는 35억, GP 원장은 아직 30억이라 ‘불일치’가 됩니다. 송금일과 입금 확인일이 다른 건 정상이라 7일은 ‘확인 대기’로만 둡니다.”

“GP가 입금을 기록하면 웹훅이 오고, 대사 이력에 불일치 다음 일치가 쌓입니다. 장부와 대사 이력은 추가만 되고 고칠 수 없습니다.”

5 / 의결권 행사

총회 안건을 내부에서 검토·결재하고, GP 총회에 직접 투표합니다

LP사후관리 → 총회 “LP연동 · 정기총회” → 찬반·검토 의견 → 투표 결재 → 승인 · GP총회 화면

말할 것

“결재가 승인된 투표안과 지금 투표안이 같을 때만 GP에 제출합니다. GP 화면에는 하늘연금 줄에 ‘LP 직접’이 붙고, GP는 이 표를 바꿀 수 없습니다.”

6 / 포트폴리오

연동 조합과 수기 조합이 섞여도 성과를 한 화면에서

LP포트폴리오 → 성과, 빈티지 · 분야 · 운용사 · 연동/수기로 모아 보기

말할 것

“배수는 출자 건 배수를 평균하지 않고 금액 합계로 다시 나눕니다. IRR은 모든 현금흐름을 합쳐 한 번 계산합니다. 엑셀 XIRR 예시값과 같게 나오는지 검증했습니다.”

“평가액은 최근 보고에 그 뒤 납입을 더하고 분배를 뺀 값이고, 보고가 없는 출자 건이 있으면 위에 경고가 뜹니다.”

7 / 청산

조건을 모두 채우면 최종 성과를 고정하고 출자 건을 잠급니다

LP조합 “한결 초기 1호”를 청산 완료로 → 출자 건의 청산 조건표 → 남은 콜 납입 → 청산 확인

말할 것

“미납 캐피탈콜, 수령 대기 분배, 확인 안 한 대사 불일치가 하나라도 있으면 청산할 수 없습니다. 확인하면 청산일 기준 성과가 고정되고, 그 뒤로는 납입·분배·약정 변경·보고를 더할 수 없습니다.”

8 / 기관 분리

다른 기관으로 들어가면 하늘연금의 데이터는 하나도 보이지 않습니다

LP로그아웃 → 바다성장출자로 로그인

말할 것

“두 기관 모두 같은 GP 조합에 출자했지만, 각자 자기 몫의 콜·분배·총회만 봅니다. 기관을 건너는 연결은 DB의 복합 외래 키가 막고, 다른 기관 주소를 직접 열면 404가 납니다.”

설계

돈을 다루는 시스템이라 지킨 것

장부는 추가만원장 · 대사 이력 · 단계 이력은 DB 트리거로 수정·삭제를 막고, 정정은 취소 행으로 남깁니다.
결재 없이 돈이 나가지 않음결재 때 숫자를 스냅샷으로 남기고, 승인하는 순간 예산 행을 잠근 채 다시 검사합니다.
세 겹의 방어선화면 검사 → 서버 업무 규칙(오류 코드와 규칙 번호) → DB 제약과 트리거.
중복 방지돈이 걸린 요청은 Idempotency-Key로, 받은 웹훅은 이벤트 ID로 한 번만 처리합니다.
숫자는 한 곳에서성과·예산·자금 계획은 저장하지 않고 계산하며, 점검 스크립트가 화면끼리 85개 항목을 비교합니다.
연동은 끊겨도 됨GP가 응답하지 않아도 LP 업무는 저장되고, 하루 1회 주기 작업과 수동 버튼이 나중에 맞춥니다.

단순화해서 밝혀 둔 가정 · GP 31개, LP 30개를 실무 확인 목록으로 따로 모았습니다. 예를 들면:

  • 결재자는 한 명 (결재선·전결 규정은 다음 단계)
  • 대사 확인 대기는 달력일 7일, 보고 기한은 분기 말 + 45일
  • 성과 평가액은 최근 보고에 이후 현금흐름을 더하고 뺀 값
  • GP 분배 워터폴은 원금 → 기준수익 → 초과수익, 캐치업·세금 없음

Next.js 16 · TypeScript · Tailwind CSS · PostgreSQL(Neon) + SQL 직접 작성 · zod · Vercel(싱가포르 서버). 차트는 라이브러리 없이 직접 그렸습니다.
